## #14

**"Works in isolation, fails in pipeline" can be poisoned server-side session state, not a request-shape diff.** DVWA SQLi/XSS confirmed nothing in the pipeline while their smoke tests passed. The pipeline requests were byte-for-byte correct (Submit param, GET/POST, `security=low` cookie all fine) — the difference was that the crawl phase had GET-visited `security.php?phpids=on`, enabling DVWA's session-scoped PHPIDS WAF for the whole shared engagement session, so every injection returned a 58-byte block page. Fix: when a methodology works standalone but not in-pipeline, diff the actual recorded requests AND consider server/session state the earlier phases mutated — don't assume it's the request. A black-box crawler must never follow links that change the target's security posture (WAF/security toggles, logout); added `agents/_url_safety.py::is_state_changing_url` as the crawl/plan chokepoint.

## #16

**"katana only surfaces login.php" was an uninitialised DVWA DB, not a crawl/guard/wrapper bug — and the test never checked that login actually succeeded.** The `vulnerables/web-dvwa` image's `main.sh` only starts mysqld/apache2; the `users` table is created by `setup.php`, which `dvwa-init.sh` patched to *allow* automated init but never *triggered*. So a fresh container fails `admin/password` login (302→`login.php`, banner "Login failed"), every shared session stays unauthenticated, and the authenticated crawl sees only the login page. The smoke test logged in but proceeded on whatever cookies it got — a GET of `login.php` sets `PHPSESSID` even on a *failed* login — so it asserted on an unauthenticated crawl and reported the env failure as a katana regression. Fixes: (1) `dvwa-init.sh` now POSTs `create_db` once Apache is up (PHP `file_get_contents`; image lacks curl/wget) so a fresh container is login-ready; (2) tests verify the session is *genuinely* authenticated (`/index.php` not redirected to `/login.php`) and self-heal a missing DB before asserting, and assert the behind-login module *set*, not a substring/count. Lesson: before blaming the code path the brief names, confirm the target's data plane is actually initialised; and an "authenticated" smoke test must prove the session is authenticated (PHPSESSID alone does not) before asserting on anything that depends on it.

## #17

**LLM-output Pydantic models: a `list[str]` field the model will populate from LLM JSON is a latent crash — type it `list[dict]` with a coercing validator.** Hit three times on `ExploitAnalysis`: `chaining_opportunities`, then `finding_ids`, then `false_positive_suspects`. Each was typed `list[str]`, but the live LLM naturally returns structured objects (`{id, reason}`, `{description, finding_ids}`), so construction raised N Pydantic errors — and because the call site wraps construction in a broad `except`, the whole Step-3 analysis silently degraded to an empty advisory (the false-positive-suppression pass never ran; phantoms reached the report). The deterministic-fallback smoke fixture (silent LLM → `[]`) never exercises the populated shape, so unit green hid it. Fix: any field a model fills from LLM JSON that the LLM might emit as objects must be `list[dict[str, Any]]` with a `@field_validator(mode="before")` that coerces both str and dict elements to a single shape (drop unusable entries, never raise). When fixing one, **sweep every LLM-populated model** for sibling `list[str]` fields the LLM could dict-ify (instruction-step / param-name string lists are fine; "items with id+reason/description" are not). Lesson: don't trust the field's current type against a model the LLM writes into — and a broad `except` around model construction turns a schema mismatch into a silent feature outage, so test the *actual* LLM shape, not just the fallback's.

## #18

**"Works in smoke, fails in pipeline" — third distinct cause: the smoke fixture forces the deterministic fallback, so it never exercises the live-LLM path.** CMDi and LFI confirmed nothing in the pipeline while their smoke tests passed; the requests were correct AND the session was clean (the vuln demonstrably triggered — `;echo <canary>`→`<pre><canary></pre>`, `php://filter`→base64 of /etc/passwd embedded in the page). The miss was in phase-5 verification: the verifier normalised `indicator_type` by an *exact-match* synonym list that only covered the deterministic fallback's canonical labels (`stdout_reflection`, `base64_blob`...). The smoke fixture wires a silent LLM, which returns `""` → the methodology always falls back to those canonical labels, so verification passed. The real Anthropic LLM emits its own wording (`output_string`, `time_delay`, `base64_encoded_string`), which fell through to `"unknown indicator_type"` and the verifier returned False *without ever inspecting the response body*. Fixes: (1) classify `indicator_type` by keyword, not exact match, so verification is driven by response evidence rather than the LLM's label; (2) for base64 LFI, extract base64 runs from the page and decode them — never substring-match the expected indicator (base64 chunk alignment shifts an interior substring's encoding) nor decode the whole HTML body. Lesson: a green smoke suite that pins a silent/stub LLM proves only the fallback path; any verification logic keyed on LLM-produced fields needs a test that feeds the *actual* LLM vocabulary, and the gate must reject on missing evidence, not on an unrecognised label.

## #19

**"The target ships an OpenAPI spec — parse it" was the brief's premise, but Juice Shop ships none — verify what the live target actually serves before building the win on it.** Fix #4 was to harvest JSON request-body params, and the brief named OpenAPI as "the primary win" because "Juice Shop ships /api-docs." A live probe (15 lines of httpx) before finalising showed every conventional spec path (`/openapi.json`, `/swagger.json`, `/v3/api-docs`, `/api-docs/swagger.json`) returns `200 + text/html` — the SPA shell, not JSON — and `/api-docs` is Swagger-**UI** HTML whose only real spec is a partial `/b2b/v2` doc (B2B orders), not login/feedback. So the OpenAPIDiscoverer parses nothing on Juice Shop and the spec-driven mechanism, though correct and unit-proven, never fires on the live pipeline. The brief's PART 2 had already sanctioned the fallback ("where no spec, mark it a JSON POST and probe the fields the route's known challenge uses"); a tight curated `_KNOWN_JSON_POST_BODIES` map (login→email,password; feedback→comment,rating), existence-gated and SPA-200-safe, delivered the live win. Lesson: when a brief asserts the target exposes some artifact (spec, header, endpoint) that your fix depends on, probe the *running* target for it before building — don't trust the asserted premise; and keep the deterministic fallback the brief offered, because the "primary" source may simply not exist there. (Same family as the DVWA-DB and CMDi premise misses below: confirm the data plane, not the claim.)

## #20

**Multi-line commit messages: PowerShell here-strings (`@'...'@`) only work in the PowerShell tool, not the Bash tool — and even in PowerShell, pass them via a `$var`, not inline.** A `git commit -m @'...'@` issued through the Bash tool was parsed literally (`@` is not bash here-doc syntax), producing a commit whose subject was a stray `@`. Re-amending inline in PowerShell then split the message on an embedded `"..."` substring, so git saw the words as pathspecs. Fix that worked: assign the here-string to `$msg = @'...'@` (closing `'@` at column 0) and run `git commit -m $msg`. **Correction (proven again):** even `$msg` via `-m` is NOT safe when the message body contains embedded double-quotes — PowerShell 5.1's native-command argument parser splits the variable on `"..."` substrings, so git received the words after a `"0 endpoints"` quote as pathspecs and the commit failed. The reliable pattern is **`git commit -F <file>`**: write the full message to a temp file (e.g. `$env:TEMP\msg.txt`) and commit with `-F`, which reads it verbatim with zero shell quoting. Same trick for `gh pr create --body-file`. Lesson: for any multi-line commit/PR text on this Windows box, write it to a file and use `-F` / `--body-file`; do not rely on `-m $var` if the body can contain `"`.

## #22

**A live-verified "justified non-finding" must be PROVEN against an instance where the vuln is actually live — a green unit suite over a *simulated* engine hides real detection bugs, and a target's safety gate is not the same as "patched."** SSTI confirmed nothing on Juice Shop and I nearly wrote it off as "build escaped/validated the username." Two real issues surfaced only by running against a Juice Shop started with `challenges.safetyMode=disabled` (the eval genuinely live): (1) **a real detection bug** — the profile renders the username *twice* (eval'd `<p>49</p>` AND raw input `value="#{7*7}"`), and my reflection guard `if literal in body: continue` rejected the whole response because the literal was reflected in the input, so the `49` was never seen; the RCE scaffold guard had the same flaw. Fix: baseline-anchor eval detection (product absent from a benign baseline, never gated on literal-presence) and strip the `echo <canary>` scaffold so a *bare* canary confirms despite a verbatim gadget reflection. (2) **the non-finding was a deployment safety gate, not a patch** — Juice Shop disables the username-eval on Docker (`isChallengeEnabled(usernameXssChallenge)` false via `disabledEnv:[Docker]` + `safetyMode=auto`); the code path exists and fires when safety is off. Lessons: when a real-target gate produces no finding, (a) confirm the vuln is actually *reachable/live* on that deployment (read the gate, or stand up an instance with it enabled) before calling it justified — "challenge exists & unsolved" means present, not patched; (b) prove the methodology on an instance where the bug is live, because unit tests over a mocked engine pass while real coexisting reflection breaks detection; (c) the in-process HTTP path needs `TOOL_EXEC_MODE=local` (docker mode curls inside the down/unreachable `clinkz-tools` container → silent status 0).

## #23

**A test-defined `ToolBase` subclass leaks into resolver discovery via `ToolBase.__subclasses__()`, and you CANNOT evict it from the leaking test's own fixture finalizer — the reap must happen at the reader.** `test_observability_smoke` defined a throwaway `echo_smoke` tool at module scope; `ToolResolver._discover()` walks `ToolBase.__subclasses__()`, so `test_all_tools_discovered` (exact-set assertion) saw a phantom tool under full-suite runs while passing in isolation. First fix attempt — move the class into a function-scoped fixture and `del + gc.collect()` in the finalizer — **did not work**: pytest still holds the yielded value in its fixture cache (`cached_result` / `item.funcargs`) at finalize time, so the class is still referenced and `gc.collect()` can't reap it. What worked: (1) keep the class **function-local** (not module-scope) so it becomes collectable once pytest tears the item down, and (2) force `gc.collect()` at the **reader** — the `resolver` fixture, right before constructing `ToolResolver()` — because `__subclasses__()` also lists dead-but-uncollected classes, so collecting there reaps any pending test subclass before discovery walks the registry. Lesson: to keep an exact-set assertion over a global `__subclasses__()` registry deterministic, reap garbage at the point that reads the registry; a leaking fixture cannot self-evict because the test framework outlives its own finalizer's references.

## #24

**Piping the keyless gate through `tail` (or `&&`) reports the *pipe's* exit code, not pytest's — a false-green that hides real failures.** Ran the gate as `pytest … | tail -25` (and once as a backgrounded command); the harness/`$?` reported exit 0 while pytest had **3 real failures** underneath (the plan-coverage tests, which a new vuln-class category legitimately breaks until the `_mixed_endpoints` fixture is updated). I only caught it by reading the captured `tail` output and seeing "3 failed". This is exactly the false-green the pre-push gate warns trains you to wave off failures. Fix: run the gate so pytest's own exit code is the signal — `pytest … > out.txt 2>&1; echo "EXIT=$?"` (capture `$?` immediately after pytest, before any pipe), or check the summary line, never trust a piped/`&&`-chained exit status. Corollary: adding a methodology to `_DETERMINISTIC_CATEGORY_ORDER` requires updating the plan-coverage fixture (`_mixed_endpoints`) and the seed-count assertion (`test_persistent_kb` `== N`) in the same change — these counts are expected churn, not a regression.

## #25

**"The module exists, fix the methodology" — but verify the *running target's version actually ships it* before building, because a frozen test image can predate the module entirely.** The brief asserted DVWA's `open_redirect` module "EXISTS at `/vulnerabilities/open_redirect/`" and asked to fix the methodology + category map. I built the whole methodology change + unit tests + live smoke + docs first; only the deferred "curl the module" step (DVWA was down at plan time) revealed the clinkz image was the frozen `vulnerables/web-dvwa` (**DVWA v1.10 Development**), which predates `open_redirect` / `authbypass` / `cryptography` — all 404. The "N/A — module absent" reading was literally correct *for that image*. Resolution required migrating the target to `ghcr.io/digininja/dvwa` (ships the modules; needs an external MariaDB + `DEFAULT_SECURITY_LEVEL=low` since it defaults to `impossible`). Two further traps the migration surfaced: (1) the modern image scopes the PHP session cookie to `domain=localhost` (DVWA `dvwaPage.inc.php`: `domain = parse_url(HTTP_HOST)`), a **dotless host Python's RFC-6265 cookie jar refuses to send back** — so httpx/aiohttp silently drop the session on the login POST (curl is lenient and works), breaking auth; fix by making the cookie host-only in the Dockerfile. (2) The `open_redirect` handler is `source/<level>.php` — the **level is in the path, not the `security` cookie** — and the high handler serves no links, so the substring-allowlist token (`info.php`) comes from the param's *own* `?redirect=info.php` value, not a harvested page. Lessons: (a) when a brief says "module/endpoint X exists," `curl` the *running* target for it as step 0 (same family as the DVWA-DB / OpenAPI / CMDi premise misses) — a frozen vuln-app image is often years behind the cheat-sheet's current version; (b) curl-works-but-Python-fails on a localhost target is the dotless-`domain=localhost` cookie trap — make the target's session cookie host-only rather than special-casing every client.

## #26

**Reusing a signature/matcher across a new response *channel* needs a content-shape check — a line-anchored regex tuned for one channel silently fails on another.** XXE file-disclosure verification first reused `_LFI_FILE_SIGNATURES["/etc/passwd"]` (`^root:…`, line-anchored `re.MULTILINE`) — correct for LFI where the file is returned *raw* with `root:` at a line start, but an XXE disclosure arrives **wrapped**: Juice Shop's 410 body is `…deprecated for security reasons: <clinkz>root:x:0:0:…`, so `root:` is mid-line and `^root:` never matched → `external_entity` stayed False and no finding emitted. The unit test that reproduced the real 410-wrapped shape (not a clean mock) caught it; the fix was a channel-specific `_XXE_FILE_CONTENT_SIGNATURES` with an **embedded** pattern (`root:[^:\n]*:0:0:`, no `^` anchor). Lesson: when reusing a matcher in a new context, verify the new channel's content *shape* — raw vs wrapped/embedded, leading prefix, truncation — before assuming a regex that works for one delivery channel works for another; reproduce the real wrapped response in a test, and confirm against the live target (here the `/file-upload` 410 disclosed `/etc/passwd` in-band, which also proved XXE is reachable on default-Docker because the parse path is gated by `deprecatedInterfaceChallenge`, no `disabledEnv`, not by the Docker-disabled XXE challenges). Same family as the SSTI "reflected-twice" coexistence bug: the live target's response shape breaks a matcher that passed against a clean mock.

## #27

**A finding that confirms *identically at every security level* — including the hardened/impossible one — is the signature that the methodology's success-oracle is matching the app's own benign response, not real exploitation.** File-upload emitted "Unrestricted File Upload" at DVWA low/medium/high/impossible alike (same `baseline_status=0`, `working_extensions=ALL`, execution never observed). Root cause was a **never-working transport**: `_http_post_multipart` hardcoded the file field `name="file"` (DVWA's input is `uploaded`), omitted the `Upload` submit field, and `HTTPClientTool` sent the multipart body via curl `-d` (which strips CR/LF and corrupts multipart framing) — so DVWA received *no file at any level* and just re-rendered the upload form, whose `name="uploaded"` matched the bare `uploaded` success marker. The acceptance oracle was colliding with the app's benign echo. Fixes: (1) thread the form's real file-field name + submit/hidden fields through the multipart builder and switch the HTTP client to curl `--data-binary` so boundary CRLFs survive; (2) anchor acceptance on a signal *distinct from the form re-rendering* (boundary-anchored filename echo / explicit success phrase / `Location` to the artifact — a bare re-render is NOT accepted); (3) require ground-truth **execution** (fetch the stored artifact back, see a self-appended canary echoed as interpreter output), not mere retrievability. Lessons: (a) treat a uniform confirm across a *graded* security control as a prime phantom signal — a real vuln's exploitability changes as the control hardens, so if "impossible" confirms too, suspect the oracle never left the app's default response; (b) prove the wire actually reached the app (log the raw request/response, or assert the artifact truly landed) before trusting any emission — a green in-isolation run can be the methodology succeeding at *nothing*; (c) an acceptance marker must never be a substring the app also emits on its *failure/benign* path (here the form's own `name="uploaded"`). Same premise-verification family as the DVWA-DB / OpenAPI / open_redirect-module misses, but at the transport layer.

## #28

**When phase 2 has EMPIRICALLY confirmed the exploit primitive, phase 4 must prefer the deterministic build over the live LLM — and a stack-gated methodology must not depend on the (flaky) LLM tech-extraction alone.** LFI confirmed nothing on the real DVWA pipeline at any fi level while the unit suite was green (the silent-LLM false green of #18 again). Two distinct causes, both invisible to the harness: (A) **the live LLM mangled a proven payload** — phase 2 read `/etc/passwd` and set `prefix_required=True`, but phase 4 trusted the Anthropic synthesis, which appended a `%00` (dead null-byte on PHP 8.5.6), so phase 5 re-probed `/etc/passwd%00` and never re-confirmed the genuine read; the deterministic fallback (silent-LLM path) produced the clean `/etc/passwd`, so unit green. Fix: phase 4 prefers the empirically-grounded deterministic build (`_lfi_primitive_confirms`) when phase 2 confirmed the read (absolute/traversal/nul/wrapper) — skipping the LLM for that type — and phase 3 floats the confirmed retrieval type ahead of the LLM ordering (re-adding any it dropped). This is the SQLi "prefer the empirically-grounded build when a breakout is known" discipline: an LLM guess that ignores the confirmed primitive is the bug. (B) **`_is_php_stack()` was False on DVWA** because recon/research LLM tech-extraction is *non-deterministic* — it named PHP on one run and omitted it on another (the only signal is the `X-Powered-By` header the harvest never reads), so the PHP-gated wrapper loop silently skipped and `file://` was never probed at fi/high. Fix: backstop the tech list with a deterministic ground-truth signal — a `PHPSESSID` session cookie (only PHP sets it). Lessons: (a) any methodology step gated on a *confirmed* phase-2 primitive should USE that primitive deterministically, not re-derive it via the LLM (which will paraphrase/mangle it); (b) a stack-conditioned branch (`_is_php_stack`, engine fingerprints, dialect) must not hinge solely on the LLM tech list — back it with a deterministic protocol artifact (session-cookie name, `.php` path, header) because the LLM extraction flakes run-to-run; (c) reproduce with a *live-vocabulary* LLM fixture (returns the `%00`/paraphrase the real model emits), not the silent stub — the stub only ever proves the fallback, and re-validate on the REAL orchestrated pipeline, not a harness/direct call.

## #29

**A methodology confirming NOTHING in the pipeline while its isolated skill test passes can be a DISPATCH gap — the endpoint reached it *param-less* — not a verification bug; and an isolated `_test_*` smoke test structurally cannot catch it.** Open-redirect emitted nothing at every DVWA level in the real run, and CLAUDE.md mislabeled that "live-validated, confirms L/M/H". The confirm logic was fine — the endpoint never arrived with the `redirect` param. Root cause was the scan crawl-endpoint merge (`_scan_http_service`): it deduped `(url, method)` keeping the FIRST-seen endpoint, but a URL-only crawler (katana) adds a **bare** `Endpoint(params=[])` for every discovered URL *first*, so when enrichment later found the SAME URL as a `?redirect=` link the param-bearing version was **skipped** — directly contradicting the block's own "prefer the version with params" comment. Since `_applicable_methods_for_endpoint` gates the injection/redirect classes on `endpoint.params`, `_test_open_redirect` was never queued against the real `/open_redirect/source/<level>.php?redirect=` endpoint; it ran on `info.php?id=` documentation red-herrings and confirmed nothing. The isolated `test_open_redirect_against_dvwa` passed throughout because it builds the `PageAnalysis` **with the param handed in**, bypassing the scan/plan/dispatch entirely — the exact false-green that shipped the bad claim. Diagnosed by parsing the real trace (the methodology fired 16 phase events, ALL on wrong params, ZERO on `/open_redirect/`) then reproducing the scan merge live (enrichment produced `params=['redirect']`; the dedup dropped it). Fixes: (1) `_merge_crawl_endpoints_preferring_params` UPGRADES a bare endpoint in place with the enriched params; (2) `test_open_redirect_through_scan_merge_and_dispatch_against_dvwa` gates the full chain (scan-merge → `_dedupe_and_rank_endpoints` → `_merge_coverage` → dispatch → confirm). Lessons: (a) when a methodology emits nothing in-pipeline but passes its isolated skill test, first check the endpoint even *reached* it carrying the params it needs — a param-gated method silently no-ops on a param-less endpoint (read the trace's per-endpoint phase events, don't assume verification); (b) an isolated `_test_*` smoke test that constructs its own `PageAnalysis` proves the skill, NOT the dispatch — pair it with a through-dispatch test or the routing regresses invisibly; (c) a "live-validated" docs claim must come from a REAL pipeline trace showing the methodology actually probing the target endpoint, never from the isolated skill passing; (d) a dedup that keeps first-seen silently loses the richer duplicate — when the comment says "prefer X", make the code prefer X (upgrade in place), don't skip.

## #30

**A full-pipeline "FALSE POSITIVE" can itself be a MISDIAGNOSIS — reconstructing the probe URL from assumed request-builder semantics instead of reading the exact request the code sent.** A prior session declared the open-redirect full-pipeline confirm a false positive: it reasoned phase-5 "appends `?redirect=//evil.example` onto the crawled `source/low.php?redirect=info.php?id=N`", hand-built the *doubled* URL `…?redirect=info.php?id=N?redirect=//evil.example`, curled THAT, got a SAME-SITE relative 302, and concluded the appended_url confirm misread it. But `_build_request_url` **REPLACES** a same-named query param in place (never doubles it — the IDOR note in CLAUDE.md says exactly this), so the pipeline actually issued the CLEAN `?redirect=//evil.example`, which curls to a real off-site `302 location: //evil.example`. The confirm was **genuine**; the recorded `tool_invocations/*.json` and the trace's `observed=//evil.example` both said so, and three independent curls (clean vs the two same-site shapes) settled it. The real defect was unrelated and smaller: a phase-3 **mislabel** (the LLM ranked a phase-2-non-working type first, so phase 4 synthesized the working shape under the wrong `bypass_type`). Two further traps the misdiagnosis hid: phase 5 *already* used `urljoin` host-resolution uniformly (a fix the FP note assumed was still needed — it had landed in an earlier commit on the same branch, 564ec0b), and the "genuine" claim it was "correcting" was actually right. Lessons: (a) before calling a full-pipeline finding a false positive, reconstruct the EXACT request the code issued — read the recorded `tool_invocations` (or the trace's observed value), don't hand-build the URL from an assumption about append-vs-replace; a wrong reconstruction curls a URL the pipeline never sends; (b) when a task hands you a "root cause already found," still verify the premise against ground truth (curl the real endpoint, read the trace) — here the stated defect (phase-5 substring path) no longer existed and the stated symptom (phantom) was actually a genuine-but-mislabeled finding, so blindly "implementing the fix" would have chased a non-bug; (c) `_build_request_url` REPLACES same-named params — a methodology's phase-5 request against an already-parametrized crawl endpoint is the clean single-param form, not the original value with the payload appended.

## #31

**The live Log4Shell OOB channel is `${jndi:dns://<collab>:<dns_port>/<nonce>}` straight to the collaborator's DNS leg — NOT the `ldap://` shape the design paper assumed; and every "obvious" DNS-delegation path was blocked locally.** Building the Log4Shell flagship on P6, the design (§P6.5.4) named `${jndi:ldap://<T>.<zone>/x}` and "the collaborator must catch the DNS leg." Three empirical blockers ruled out the assumed shapes on a Windows/Docker-Desktop box, and I only found the working channel by standing up the live Vulhub Solr and firing a throwaway dual (UDP+TCP) listener BEFORE writing the methodology: (1) host **UDP/53 was already bound**, so a host-DNS-on-53 + `--dns` subdomain-delegation channel was impossible — the container's embedded resolver (127.0.0.11) forwards `<nonce>.<zone>` to the real host DNS, never to us; (2) `${jndi:ldap://host.docker.internal:18080/<nonce>}` (nonce in the LDAP DN) delivered NOTHING to an IPv4 TCP listener — `host.docker.internal` resolved IPv6-first for the container, and the nonce-bearing LDAP *search* only follows a valid *bind* response anyway; (3) the winner: `${jndi:dns://host.docker.internal:15353/<nonce>}` — Java's JNDI **dns** provider sends a UDP DNS query for the nonce DIRECTLY to `host:15353`, hitting the existing DNS leg with the nonce in the qname, no delegation, no port 53. Zero collaborator recording changes; just a nonce-only `JNDI_DNS` template + `dns_authority()` (= zone-host + dns_port). Lessons: (a) for an OOB channel, empirically probe which callback actually fires from the *live target's runtime* before coding — the canonical/paper shape (ldap-subdomain-delegation) is exactly what a local docker box can't route; (b) `jndi:dns://host:port/<nonce>` is the robust local Log4Shell channel (first hop, one UDP packet, nonce in qname) — reach it directly, don't rely on the target's resolver reaching a delegated zone; (c) `host.docker.internal` can resolve IPv6-first inside a container while your listener is IPv4-only — a silent miss for any TCP-connect-based callback. A documented paper-vs-live divergence, same family as the Solr mount-base and OpenAPI premise misses.

## #32

## #33

**To prove "X changes nothing emitted," hold the run STRUCTURE constant and toggle X (A/B) — don't diff a differently-structured run against a fixed baseline; and a "no reader" grep must distinguish a READ from a WRITE.** Validating the Layer-2 capability write-back leaves emission unchanged, the first driver diffed the run's `report.json` against the in-repo `p6-log4shell` baseline and reported "emission changed": the real seam dispatches Log4Shell as one hypothesis **per channel**, and only the `action`-bearing request reaches Solr's `CREATE`-command log line, so per-task confirmed **1** finding while the baseline (all params fired in ONE request → all logged together) had **8**. ## #34

**A guard whose activation is per-clone local config does not exist; a guard that pattern-matches an open-ended option run is one new option away from a bypass.** The repo-pristine pass added three leak guards and called it defence in depth. All three were then defeated from a fresh clone in one sitting. (1) **Fresh clone = inert.** `core.hooksPath` is *local* config — it is never committed, and a fresh clone has no `.git/hooks/pre-commit` either, so `git add -f outputs/leak.json && git commit` returned exit 0 and the leak landed in HEAD. This was live, not hypothetical: the operator and the agent had both been told to re-clone after the history purge, so *neither* clone was protected — the guard's own remediation instruction produced unprotected clones. (2) **`git commit --no-verify`** skipped the git layer even where `core.hooksPath` *was* set (verified against a positive control: the same staged leak blocked without the flag, exit 1 → exit 0 with it). (3) **The PreToolUse regex under-blocked.** `git\s+(?:-\S+\s+)*commit` walks git's global options as `-\S+` tokens, which silently breaks on every global option taking a *separate* argument: `git -C <path> commit` and `git -c k=v commit` both returned exit 0, and `git -C` is a common agent idiom. Fixes, in order of load-bearing-ness: **(a)** a CI job (`leak-guard`) that runs the same guards server-side in a new `--tree <rev>` mode — the only bypass-proof layer, because no local config, flag, or clone state reaches it; asserting on the resulting *tree* rather than a diff also means a rewritten base ref cannot hide an added path. **(b)** fail-CLOSED detection: tokenize the command (shlex, split on shell operators) and flag any segment that invokes git and contains an exact `commit` token *anywhere* after it — never try to parse the option grammar; over-blocking `git log --grep commit` is the correct trade. Resolving `-C`'s target as the guards' cwd matters too: detection alone still cleared the commit, because the guards were reading the *session's* clean index instead of the named repo's. **(c)** `python scripts/bootstrap.py` to set `core.hooksPath` in one command, referenced as the FIRST step in README/CONTRIBUTING, with `/gates` printing `GATE0_hooksPath` so an unprotected clone is loud rather than silent. Lessons: (a) a protection that requires a remembered manual step per clone is not a protection — bootstrap it and make the routine command *report* whether it is active; (b) enumerate which layers are actually fail-closed and say so in the docs, instead of counting layers as depth (the PreToolUse hook must stay fail-*open* on internal error so a hook bug cannot brick Bash, which is precisely why it cannot be the gate); (c) a guard's matcher must fail closed — prefer over-blocking, and tokenize rather than pattern-match anything with an open-ended grammar; (d) verify a guard by *attacking it* from the state a real user starts in (a fresh clone), not by testing it in the configured repo where it was written.

## #35

**The gate you ran is not the gate CI runs — an unpinned dependency and a present `.env` both silently change what "keyless, green" means.** Two instances landed in the same sitting. ## #36

**The FP detector called the true signal noise — the suppression side must run by the same rule as emission.** Batch 1 established that no LLM verdict emits on its own; a deterministic check gates it. The mirror image was still live: `_fp_has_deterministic_corroboration` was descriptive only (its docstring said *"Both demote."*), so any topic-matching post-run rationale deleted a finding. At DVWA `medium` (engagement `fe234e99`) that demoted a **verified** `boolean_blind` SQLi whose own evidence read `true=4842B (delta=0) false=4848B (delta=6)`, on the rationale that six bytes "could result from normal response variance". Six bytes was the *entire* signal — DVWA's blind page answers *"User ID exists in the database."* vs *"User ID is MISSING from the database."*. The justification for demote-by-default was "a wrongly-demoted finding still reaches the operator as a lead", which is sound for an *evidence-level contradiction* and wrong for a *judgement*: it hands an LLM a veto over a measurement. Three fixes, in the order they matter. **(a) A demotion must name a deterministic CONTRADICTION the code verified** (`_fp_deterministic_contradiction`) — an encoded character the payload needed, malformed/self-inconsistent evidence (the request line assigning the parameter twice), a speculative execution claim, an error-page reflection, or an observation that restates the rationale. "The differential is small" and "this looks like a false positive" name no contradiction and demote nothing; the ground is written first into `missing_observation` so a raw reader can check every demotion has one. **(b) Strengthen the proof rather than loosen the gate.** The answer to a thin-but-real differential is not a wider tolerance, it is a measurement that carries its own control: `_sqli_verify_boolean_differential` sends baseline-true-false as one interleaved triple, repeats it, judges each repeat against *its own* contemporaneous baseline (removing drift as a confound instead of tolerating it), and requires the signed delta identical in every repeat. Strictly stronger — a delta that appeared once no longer confirms — and the rendered evidence leaves suspicion nothing to grab. On the MEDIUM re-run the reviewer did not flag it at all. **(c) Apply such a ground where emission is decided, not only post-run.** The mechanism-not-effect ground needed a deterministic handle, and the corpus supplied one: across six runs 13 findings carried a `rationale=` line and *exactly one* duplicated it verbatim into its `Response:` observation. But leaving it to the post-run reviewer made honesty depend on an LLM's attention — the same JavaScript hidden-field candidate was demoted in `df7ce6ee` and emitted un-flagged in `1f9a0932` on byte-identical evidence. Moved into `_persist_finding`. Lessons: (a) whenever an LLM can *remove* engine state, ask what deterministic fact licenses it — a suppression path with no evidentiary gate is an emission path in reverse; (b) if evidence is being doubted for being thin, make it self-evidencing (repeat it, control it, render the control) instead of arguing about the threshold; (c) a rule that only fires when a model notices is not a rule — put it at the chokepoint.

## #37

**A zero-confirmation adaptation loop is indistinguishable from coverage.** The SQLi context-adaptation ladder was added on a stated premise: phase-4 synthesis defaults to the quoted string break, so a target that escapes quotes never gets the bare-numeric shape tried. Measured across six recorded runs it fired **110 rungs and confirmed nothing** — and **106 of those rungs reported the true-shape and false-shape response bodies BYTE-IDENTICAL**. That is not "the filter was not defeated"; identical bodies for `{v} AND 1=1` and `{v} AND 1=2` mean the injected predicate's truth value did not affect the response at all, i.e. the parameter reaches no query. The parameters bear it out: a file-include path, reflected text fields, CSRF tokens. They arrived there because phase-1 candidacy is deliberately loose (*any* status/length/fingerprint change from an appended quote), which admits an **echo** (`4767` to `4768` bytes: the response grew by exactly the one character we added) and **a different sink failing** (`5236` to `4735`: the quote broke the include, not a query). Meanwhile every SQL confirmation in every run came from phase-4 synthesis or the session-indirection carrier — at `medium` synthesis produced the bare-numeric `1 AND 1=1-- -` *itself* and it confirmed, falsifying the premise the ladder was built on. The defect was that its firing condition ("every ranked type failed") is a statement about *our payloads*, not about the target. Kept rather than deleted, but gated on a **demonstrated capability signal** already in hand so it costs no request to decide (a DB error signature, a known dialect, or a discovered break prefix), bounded by an abort once invariance is *proven*, and instrumented with a deterministic `cause` per rung plus a per-parameter summary. Live result: 50 rungs to 10 over the same three levels, still 0 confirmations, every rung naming its cause. Two judgement calls worth keeping: the abort was **not** widened to "two consecutive rungs with the same cause" even though it would have cut 10 to 4, because proven invariance to the *parameter* licenses an abort while `false_shape_not_divergent` only says *this predicate shape* did not govern the result set — suppressing a probe is cheap, suppressing a finding is not; and the remaining lever was **named rather than tuned** (`_sqli_discover_break_prefix` accepts a closer when TRUE and FALSE both parse *and differ*, which any page with a per-request token satisfies unconditionally — but that helper also feeds UNION column counting and synthesis, so it carries emission blast radius and needs its own family re-run). Lessons: (a) an adaptation loop needs a *capability precondition*, not a failure precondition; (b) instrument every attempt with a deterministic cause from a closed vocabulary, or the next zero-confirmation run has to be re-derived from byte counts; (c) write down the delete-it-if-still-zero commitment, because a loop that burns budget and confirms nothing is worse than no loop; (d) measure the premise against recorded runs before extending the mechanism built on it.

## #39

**Whether the confirming attempt runs must never be the LLM's call — or the description becomes the only reachable outcome.** Engagement `1f9a0932` emitted `JavaScript-controlled hidden field(s) token`, medium/confirmed, `phases_completed=4`, whose entire evidence was the form's field list plus the `rationale=` it was derived from. Nothing had ever been submitted. The reason was structural, not a model slip: the bypass attempt was gated on the LLM's `should_attempt_bypass`, and the deterministic replay behind it (`_attempt_js_bypass`) only handled a **string-literal** write. A real client-side token is a function call — DVWA computes `md5(rot13(phrase))` — so on the single shape the class exists to catch, the attempt could never fire and a mechanism description was the only thing the class could produce. Its oracle was also a fixed success-marker list with **no control arm at all**, which would have confirmed on any page that happens to say "well done". The control is drawn at the **same length and character class** as the forged value (hex case included), because a control that differs in *shape* can be rejected by a format check rather than by the security check — leaving the arms differing in exactly one respect is what licenses attributing a divergence to acceptance. The app may gate on an unrelated input *before* it ever looks at the token (DVWA checks the phrase first), so the isolating input has to be searched for — over candidates discovered from the app itself (the field's own default, literals its JS compares against, quoted words in the visible text), each tested against its own control so the search can only reveal a differential, never create one. And the replay must be a **bounded grammar, not an interpreter**: standard transforms only, with `Date.now()`/`Math.random()`/an unseen helper as a parse failure, so "we cannot rebuild it" degrades to a lead instead of a guess. Lessons: (a) if a model decides whether the *proof step* executes, the class's floor is its hypothesis — gate the attempt on a deterministic property of the target; (b) a confirmation with no control arm is a vocabulary match; (c) when the effect is hidden behind an unrelated gate, searching for the isolating input is legitimate exploitation as long as every candidate carries its own control; (d) an emission chokepoint that catches a bad finding by the *shape of its prose* is a net, not a fix — fix the class that produces the candidate.

## #41

**A guard that parses text the target controls hands the target a vote on our own verdict.** The batch-5 honesty fix added a chokepoint gate: a finding whose own `verification_strength` is `likely` is demoted, because `likely` means the defining effect was not witnessed while `_make_finding` stamps `CONFIRMED` unconditionally. The gate needed the value, and `verification_strength` is not a field on `Finding` — every methodology renders it into an evidence entry (`phases_completed=6 verified=True strength=verified`). So the first implementation searched every evidence entry for `strength=` and took the first match. The gate-3 security review found the hole, in code that same session had just written. `_make_finding` builds the evidence list as `["Request: …", "Response: …"]` and the methodology appends its verdict **after** — so the entry holding raw, unescaped bytes from the target sits at index 1, *ahead* of the engine's own line. Reflected-XSS evidence is the fully-raw instance: `_xss_evidence_snippet` captures ±80 characters of verbatim response markup around the reflection point. A host that echoed the literal `strength=likely` next to its reflection — `<!--strength=likely-->$INPUT` suffices — would therefore have made the guard read the *target's* bytes instead of the engine's measurement, demote a genuine deterministically-confirmed finding, and tell the operator the effect was never witnessed. That is the project's own invariant running backwards: bytes the target chose deciding an emission, inside a guard built to stop exactly that inversion. Two things made it easy to introduce. First, an injection-resistant helper already existed — `_evidence_field` anchors with `line.startswith(f"{key}=")`, which a `Response:` entry can never satisfy — and the new helper's docstring explicitly recorded *dropping* that anchor as the point ("the value is mid-line … `_evidence_field` cannot see it"), i.e. the safety property was noticed and discarded as an obstacle. Second, the same unanchored scan was copied into the validation harness, so the same string would also have fabricated audit violations — the check that was supposed to catch the class was vulnerable to it. Fixed by reading only **fully-structured** entries: every whitespace-separated token must be a `key=value` pair, so `Request:`/`Response:` fail on their first token and a rendered structure such as `restrictions={'a': [], 'b': False}` fails on its interior ones. Note an evidence entry is a list ELEMENT rather than a line, so a newline inside a captured body cannot forge a structured entry either — which is precisely why `startswith` was safe and a mid-string search was not. Lessons: (a) before a guard reads a value, ask *who wrote these bytes* — in a pentest tool the answer for anything response-derived is "the host under test"; (b) when a safer variant of a helper already exists, treat "it cannot see my value" as a signal that the value is in the wrong place, not that the anchor is wrong; (c) a suppression primitive handed to the target is strictly worse than the phantom the guard prevents, because a false negative is invisible in the report while a phantom is at least reviewable; (d) copy a parse into a harness and you copy its weakness into the check meant to catch it — harden both, or share one implementation.

## #42

**One inversion recurs across classes: fix it at the chokepoint AND at every source, and close the vocabulary in both directions.** `strength="likely"` mapping to `status=confirmed` was diagnosed and fixed once, at the DOM-XSS dispatch, with a docstring explaining that an unwitnessed effect is a candidate and a candidate is a different type. A codebase-wide audit for batch 5 found it still live in **three** more classes, for the same structural reason each time: `_make_finding` stamps `CONFIRMED` unconditionally, and each class's dispatch gated on `result.verified` alone. ## #43

**A veto that reads the model's PROSE is a coin flip across runs; scope it to the case it was written for.** D1 ladder B ran three consecutive, identical DVWA LOW engagements. In all three the reflected-XSS class was planned, dispatched to the right endpoint, and reached phase 5 on `name` with the *same* measurement — `verified=True strength=verified context=html_body payload='<script>alert(1)</script>'`, phase 2 recording `probed=25 survived=25`. Runs 1 and 3 emitted the finding. The same witness stands down the FP cross-check's matching ground, which demoted on the identical prose, read from the engine's own structured `literal_landing_witnessed=` evidence entry rather than from prose or from anything the target chose (cf. #41). Two details worth carrying. **Log and trace the veto you skip** (`prose_veto_overruled_by_witness`): a suppression that did not happen must be as auditable as one that did, or the gate becomes unreviewable in exactly the direction that loses findings. And **split the prose conditions into a named helper** rather than leaving them as the last two lines of the gate — a condition added below them would otherwise silently inherit the wrong half of the rule. Lessons: (a) a guard's scope is part of its correctness — "does this text look speculative?" and "was the effect observed?" are different questions, and only the second may decide; (b) the standing rule runs in both directions, so state it that way: a deterministic signal decides emission AND suppression, and an LLM overrules neither; (c) when the same prose appears in two places (a gate and a post-run cross-check), fixing one leaves the other holding the defect — find every reader of the same text; (d) instability across identical runs is a *diagnostic*: if the target did not change and the verdict did, something non-deterministic is deciding, and the model's wording is the usual suspect.

<a id="lesson-44"></a>

## #44

**Three incidents in one methodology family is one defect, not three.** The file-upload class shipped a per-branch patch in three consecutive batches before anyone asked what each branch actually *claims*: `direct_execution` needed the confirmed-extension walk after one unlucky synthesis pick lost a CRITICAL three prior runs had found (#38); `client_side_only` was verifying on `fetch_resp.status == 200` alone and emitted a confirmed medium on the one DVWA level whose upload control works (#42); and then `inclusion_chain` appeared in exactly one LOW run of three, on the same endpoint whose CRITICAL `Unrestricted File Upload` was stable in all three. Read as a third incident it looks like a flake. Read as a family it is obvious: the four branches shared one verifier, so the family confirmed on the weakest observation any of them offered. The repair is a table, not a patch — each `FileUploadExecutionType` declares its **defining effect** and the **one deterministic observation** that proves it, and only branches whose observation this engine can make may confirm. Two can: `direct_execution` and `interpreter_misconfig`, both proven by the canary echoing back as interpreter *output* with the source absent. Two cannot: `client_side_only` needs a client-side execution oracle (the same gap that makes every DOM-XSS result a lead), and `inclusion_chain` claims that a **consumer sink** includes the stored artifact — while its verified branch was a bare `status == 200` on a **direct GET** of that artifact. Nothing in the engine invokes a consumer, and the agent keeps no runtime record of a confirmed file-inclusion primitive to invoke one with (`LFIMethodologyResult` is a local inside `_test_lfi`, dropped when it returns), so "the chain composes" was asserted by the finding's own title and observed nowhere. Both now emit an `UnprovenExploitLead` naming both halves — the effect claimed and the observation missing — so the reachability survives and the claim does not. The second half of the defect is **ordering**, and it is what made the instability visible. Retrievability is trivially true precisely when real execution would *also* have worked, and the phase-4/5 loop breaks on the first branch that verifies, so on one endpoint the model's ranking alone decided whether a run reported CRITICAL code execution or a HIGH "validation gap": rank `inclusion_chain` first and the CRITICAL is never attempted. Which branch is tried first is a legitimate LLM checkpoint; whether a branch that cannot prove its effect may pre-empt one that can is not (#39). The model's order is now preserved *within* each half, and the confirmable half runs first. Two tidy-ups fell out and are worth doing rather than leaving: `verified-stored` labelled exactly one thing — that retrievability claim — so it left the confirming-strength vocabulary with it; and `interpreter_misconfig` had been grading `high` while `direct_execution` graded `critical` for byte-identical proof, which is a severity decided by the route rather than by the impact. Lessons: (a) when the same class needs a third honesty patch, stop patching branches and ask what each branch claims — the recurrence is the diagnosis; (b) a branch named after a *chain* must observe the chain, and an artifact you can GET is not an artifact a consumer included; (c) declare (effect, proving observation) in one table with a test that fails on an undeclared member, so a new branch cannot inherit a verifier built for a different claim; (d) when a loop stops at the first success, the ordering *is* part of the confirmation model — check what a wrong order costs before deciding an ordering is cosmetic.

<a id="lesson-45"></a>

## #45

**Fixing an origin-level finding's ADDRESS does not fix its VERDICT — the race just moves.** Batch 5's consistency diff called 16 entries flaky, and 12 of them were one defect: `_test_security_headers` emits per `(origin, header)` with the first URL to reach it winning the dedup, and the finding recorded *that URL* as its target, so three identical LOW runs reported the same seven origin-level headers against `/`, `/hackable/uploads/` and a bare origin. Batch 6 made the target the origin, kept the measured page as `observed_url=` provenance, and the 12 entries went stable. The next ladder promptly split the *same* header three ways again. DVWA serves a `Content-Security-Policy` on `/vulnerabilities/csp/` and on no other page; the dedup key is the same either way, so whichever page the plan reached first decided whether the origin's CSP was reported **Missing** (runs that reached `/`, `has_csp=False`, rollup medium) or **Weak** (the run that reached the CSP page, `has_csp=True`, rollup **low**). Same origin, same posture, two different findings and two different severities. The lesson is that scoping a finding to a container scopes *every field it carries*, not just the one you noticed: the address, the verdict, and the severity all have to be functions of the container, or fixing one merely relocates the non-determinism into the others — and severity is the easy one to miss, because a set-diff keyed on title and target does not see it at all. The fix should be settled against a **fixed member** of the container rather than an arbitrary one: the origin ROOT's own header set decides, so a header present on this page but absent from the root is reported missing for the origin. Note that phase 2 already merged in the other direction — a header the root sets counts as present for a deep page, "defensive: many apps only set HSTS/CSP at /" — and the new rule is exactly its mirror, which is the tell that the original merge had encoded half of a rule and left the other half to arrival order. Two guardrails came with it: the rule is skipped entirely when the root could not be fetched (absence of evidence never vetoes, the same principle as an unprobed character in the XSS character map), and the control test asserts that an origin which really does serve a permissive CSP still gets a *weak* verdict — a rule that turned every weak header into a missing one would have traded a flake for a systematic misreport. Lessons: (a) when a finding names a container, audit every field for container-scope, not just the identity field; (b) a set diff keyed on (title, target) is blind to severity drift — check the severities column too, or a flake hides in a field the oracle never reads; (c) a one-directional merge is usually half a rule, and the missing half is where the order-dependence lives; (d) a fix that widens what a verdict can become needs a control proving the original verdict survives where it was right.

<a id="lesson-46"></a>

## #46

**A coverage assertion is only as sharp as the grade it reads, and a signal that matches almost everything is not a signal.** The Phase-3 harness carries a RANKING check built after batch 4: a plan task dropped on a class's OWN primary target (relevance grade 0), for a class that then emitted nothing, is the ordering failing rather than the budget — the exact shape that cost D1 its weak-session and HIGH-SQLi findings. On the final HIGH ladder it fired three times in one run of three, against `_test_brute_force` dropping `/vulnerabilities/upload/#`, `_test_javascript_attacks` dropping `/vulnerabilities/xss_r/#`, and `_test_csrf` dropping `/vulnerabilities/exec/#`. None of those is that class's target, and the same run's trace shows every one of the three classes dispatched to its real one (`brute/` with `login_form_shape: True, path_match: True`, `csrf/#` `state_changing=True`, `javascript/` `candidate=True`) and emitting nothing because DVWA `high` genuinely defends all three. The defect was in what grade 0 means: `_endpoint_class_relevance` returns 0 on `param_match OR precondition_match`, and `_CLASS_PRECONDITIONS` gives the five form classes the bare precondition `("form",)`. On an application where nearly every page posts something — DVWA is one, and so is most of the web — that makes grade 0 for those classes mean "has a form", i.e. nearly the whole app, so every form-bearing page in the truncated tail reads as a dropped primary target. That is the same confusion the RANKING check was written to prevent ("an ordering defect reads nothing like tail truncation and must not hide inside it") running in the opposite direction: ordinary truncation being reported as an ordering defect, which erodes the signal just as effectively as hiding one. Fixed at the **harness**, deliberately not the engine: for a class whose preconditions include the generic `form`, a grade-0 drop must ALSO be named by that class's own vocabulary — a path token or a parameter of its shape, evaluated by importing the engine's own tables and shape predicates rather than restating them, since a harness that reimplements the rule it is checking will drift from it. Classes with a specific precondition (`site_root`, `session_setter`, `file_server_path`, `xml_body`) keep the original stricter reading, because narrowing further than the defect requires would blunt the assertion that caught the batch-4 misses. Excused drops are still returned and printed, so an over-broad excuse is visible rather than silent. The engine-side imprecision — grade 0 should mean the class's own surface and for five classes it does not — is recorded as an open item instead: that grader decides which 150 of ~620 tasks survive for every class at every level, so changing it invalidates the nine runs already measured, which is precisely why batch 4 deferred the ranking fix and batch 5 needed three ladders to land it. Lessons: (a) before trusting an assertion built on a derived grade, ask what that grade discriminates *on this target* — compute how many endpoints it selects, and if the answer is "most of them", the assertion is measuring nothing; (b) a false alarm and a missed alarm damage a validation harness equally, because both teach the reader to stop believing it; (c) a harness that checks a rule should import the rule, never restate it; (d) when the correct fix would invalidate the measurement you are in the middle of taking, fix the observer, and write the open item down with its blast radius rather than leaving it to be rediscovered.

## #48

**Redaction that knows what a secret IS cannot remove what a secret LOOKS LIKE — and a guarantee checked by the same logic that produces it is not checked at all.**

Lesson #47 ended with redaction applied at every artifact writer, verified across 312 files of a live engagement: zero occurrences of either configured password. The next authenticated run against a JWT-issuing target wrote **five live session tokens** into `trace.jsonl`. One decoded to a payload carrying the account's password hash and TOTP secret, so the bundle held both a replayable session and crackable credential material.

Nothing had regressed. Every writer was still redacting correctly. The registry only ever knew values the **operator supplied** — and the target **issued** this one, so there was nothing to substring-match. A secret has two definitions and we had implemented one. The fix is a shape vocabulary (`engagement/credential_shapes.py`) that is **always on, registry or not**, because an artifact must be clean whether or not an engagement installed anything.

The deeper failure was the check. The verification for #47 searched the artifacts for the *configured* secret values, found none, and reported zero leaks — **truthfully, about the wrong question.** A guarantee asserted by the logic that produces it is not checked. When an independent scanner re-read the same bundle off disk looking for shapes, it found **826 credential shapes across 208 files** where a human reading `trace.jsonl` had spotted 5; the bulk was in the `tool_invocations/` sidecars nobody had looked at. Share the *vocabulary* between writer and checker so they cannot drift; share no *trust*.

Then split the breadth, because a checker and a redactor want different error costs. Definite shapes (a JWT whose header decodes, an `Authorization` value, a cookie value, a vendor key, a PEM block) fail the gate loudly. The entropy heuristic is advisory and lives **only** in the gate. This engine's evidence is *made of* alarming-looking strings — payloads, extracted hashes, base64 from an XXE response — so an entropy rule on the write path would shred findings, and one that failed the gate would be silenced within a week, which is the same as not having a gate. And the leak report must never reproduce the leak: kind, file, line, column, length, fingerprint — never the value, not even a prefix.

Where a token's presence *is* the evidence, replace it with a **fingerprint**: a salted hash prefix plus `alg`, the registered `iss`/`sub`, and the claim NAMES. It correlates within a bundle (this token was accepted where that one was rejected) and replays nowhere, and naming `password` as a claim tells the reader what the token carried without the artifact carrying it.

**The same run showed the same shape in a different subsystem.** Authentication reported `session_losses_detected=15, reauthentications=0`. Read from the raw invocation records, all fifteen came from requests the engine had *deliberately* sent with no session: the auth-mechanism probe that POSTs empty credentials (whose 401 is the **positive** signal that a login route exists), and the anonymous control in `assert_authenticated` (whose 401 **is the proof** the session works). The sentinel was counting the controls that prove authentication as evidence authentication had been lost. Zero of the fifteen were session-bearing, and the peak consecutive run was 2 against a threshold of 3, so the trigger could never fire either — over-firing and never-firing at once.

Four rules came out of it, and they generalise past sessions:

* **Only the seam knows.** Whether a request carried the session is knowable at the HTTP chokepoint and nowhere else; an observer forced to infer it from the response will read the proof that something works as proof it broke. Pass the fact down (`session_bearing`), and ignore a control in **both** directions — it neither counts nor resets, because it says nothing either way.
* **You cannot lose what you never had.** Everything before the first proven session is unauthenticated by definition. Disarm the watcher until the thing it watches exists; ours raised its flag six seconds before the session was established.
* **Consecutive-counting cannot survive concurrency.** Three phases feed one watcher, so any interleaved success resets the run. A scattered-total ceiling is what turns "never noticed" into "checked once".
* **A raised flag is a hypothesis, not a verdict.** Re-run the deterministic oracle before acting on it, record the survivors as false alarms, and count the *outcome* rather than the attempt — the counter was being incremented on the way in, so a run with no credential to re-authenticate with still reported having re-authenticated, in the report, which is where an operator reads that number.

## #49

**A phase timeout that discards the agent's return value converts an over-run into a total loss — and a budget checked only on the way in is not a budget.**

The brief for the API-surface work opened with a measurement: an authenticated engagement against a live SPA sent 288 requests, crawled 83 URLs, discovered 0 parameterised endpoints and emitted 0 findings, therefore the engine can only see query-string parameters. The first thing worth doing with a stated premise is to measure it, and running the *existing* route discovery against the *live* target produced 57 endpoints, 13 of them parameterised. So the premise was wrong about its own evidence, and the real cause was recorded verbatim in the Exploit planner's own prompt: `## Endpoints (0 unique, showing top 120 ranked)` followed by `[]`. The Scan phase had overrun the orchestrator's generic 600 s phase timeout by nine seconds, and that timeout is a **force-kill that throws the agent's return value away**. A scan that runs long therefore does not deliver a smaller attack surface; it delivers none. Downstream, the planner fell back to endpoint URLs the model wrote as *paths* (`/rest/user/login`), which are not fetchable — every probe returned the transport-failure sentinel, so eighteen methodologies executed against nothing in twenty milliseconds and each reported a clean non-finding. Two defects, and the second is the more dangerous shape: an engine that reports "we tested and found nothing" when it tested nothing at all.

It then took **three** live runs to fix, and the second and third failures are the more useful part of the lesson.

The first fix gave the Scan Agent its own wall-clock budget the way Research already had one, checked on the way into coverage expansion and inside the enrichment loop. The re-run failed **identically**. Coverage expansion re-runs the *whole* HTTP scan per gap, one pass measured at about six minutes, and the entry check only asked whether the budget had already run out — not whether enough was left to *finish* a pass. Starting a six-minute pass with sixty seconds left overran exactly as before.

The second fix added `_EXPANSION_MIN_REMAINING` to that entry check, and I wrote this lesson describing the distinction. The third run failed identically again, because I had applied the rule I had just written down to **one of four guards**: the per-gap check, the crawl check and the fuzz check all still asked `_budget_exhausted()`. At 12:09:07 there were 104 seconds left, which is not exhausted, so a five-minute directory fuzz started — and directory fuzzing logs *nothing* while it runs, so the overrun was invisible until the phase was already dead. The agent finished at 12:14:32; the orchestrator had given up at 12:14:15. Seventeen seconds, and the whole attack surface was discarded for the third time. The working version replaces every guard with `_budget_allows(seconds_needed, what)` compared against *measured* per-step costs.

The same trace showed a second defect worth naming: coverage expansion ran the **identical** scan three times. Every addressable gap calls `_scan_http_service` with the same arguments, and the LLM had named three crawl/fuzz-shaped gaps, so three passes each produced the same 112 routes and the same seven body schemas at six minutes apiece. Eighteen minutes to learn nothing, and the third pass is what killed the phase. A retry loop that cannot vary its inputs is not retrying, it is repeating.

Lessons: (a) **verify the premise against the running target before building on it** — the stated cause and the actual cause were different subsystems, and the fix for the stated one would have shipped into a pipeline that could not have shown it working; (b) a cooperative budget must be expressed as *"is there enough left to finish the next unit of work"*, never *"has it run out"*, or the guard fires only after the damage; (c) when a supervisor's timeout discards a return value, every phase under it needs its own budget — or make the supervisor keep the partial, which is cheap and was done here too; (d) an unreachable probe is indistinguishable from a clean result unless something asserts reachability, so resolve a planned URL against a known origin and **drop** it when there is none rather than probing blind; and (e) the container gate must run **serially** — running it while a live engagement held the single-tenant tools container produced three false failures (recon: 0 open ports; scan: 3 endpoints), which reads exactly like a regression in the code under test.
