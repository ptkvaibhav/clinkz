# Lessons (index)

A small, append-only archive so the same error is not made twice.

- **Consulted** during planning ONLY when a task resembles a past failure. Not
  read by default — do not open it for unrelated work.
- **Appended to** ONLY after an error worth not repeating.
- Each lesson has a **stable id** (`#14`–`#34`) cited elsewhere as `LESSONS #N`.
  Ids are historical — do NOT renumber (the sequence begins at #14; earlier ids
  are retired). Full narratives live in
  [`docs/lessons/README.md`](../docs/lessons/README.md); this file is the index
  (title + the rule each produced). Append a new lesson with the next id, add its
  narrative there, and add a one-line pointer here.

- **#38 — Accepted-by-the-store is not executed-by-the-server, and a path fragment is not evidence about a route.** Phase 2 learns which upload extensions were *accepted*; only the server's handler mapping decides which RUN (`.phtml` uploads fine under `<FilesMatch \.php$>` and is served inert), so walk the empirically confirmed set instead of trusting one LLM pick — a contract skill must not need a lucky guess. - **#39 — Whether the confirming attempt runs must never be the LLM's call.** A methodology whose *attempt* is gated on a model's opinion has the description as its only reachable outcome: the JS class asked the LLM `should_attempt_bypass` and its replay handled only string-literal writes, so on a real computed token (`md5(rot13(phrase))`) it never submitted anything and emitted the mechanism instead. Drive the attempt deterministically (whenever the primitive is replayable), make phase-N raise without the confirmation, and give the confirmation a control that differs from the payload in exactly one respect — same length AND character class, so a rejection cannot be about shape. → [narrative](../docs/lessons/README.md#lesson-39)
- **#40 — A class floor guarantees a class a task, not a task where the class can fire.** Three missed findings across four D1 runs (`weak_id` 1/3, `brute/` 1/3, `sqli/` 0/1) all came from one place: the plan cap drops ~480 of ~620 tasks, and the relevance grade "shape-compatible but unremarkable" is a huge tie bucket broken by *crawl order*, which varies per run. The endpoint that can actually confirm sat in that tie. Rank on a signal the scan already observed (a cookie actually set) rather than a path substring, and break ties on something stable — a coverage floor that ignores where the vuln lives is a coin flip wearing a guarantee. → [narrative](../docs/lessons/README.md#lesson-40)
- **#41 — A guard that parses text the target controls hands the target a vote.** The new "`likely` never confirms" gate read `strength=` out of the finding's evidence — but `_make_finding` puts the raw `Response:` bytes at index 1, *ahead* of the engine's own verdict line, so a host echoing `<!--strength=likely-->` beside its reflection would have deleted a genuine, deterministically-confirmed finding. Read a typed field, or restrict the parse to entries that are wholly `key=value` (a rendered dict or a `Response:` line then cannot qualify) — and remember an evidence entry is a list ELEMENT, so `startswith` is injection-resistant where a mid-string search is not. A suppression primitive handed to the host under test is worse than the phantom the guard prevents. → [narrative](../docs/lessons/README.md#lesson-41)
- **#42 — One inversion recurs across classes; fix it at the chokepoint AND at each source.** `strength="likely"` mapping to `status=confirmed` was fixed once at the DOM-XSS dispatch and was still live in three more classes (upload `client_side_only`, reflected XSS in JS/DOM context, the sqlmap fallback) because `_make_finding` stamps CONFIRMED unconditionally and each dispatch read only `verified`. Close a vocabulary in BOTH directions with a test that fails on any unclassified literal — a deny-list of "anything but `verified`" would have demoted `dom_redirect`, a genuinely witnessed effect. And parse the AST, not a grep: both live inversions were ternaries whose losing branch a grep for the assignment misses. → [narrative](../docs/lessons/README.md#lesson-42)
- **#43 — A veto that reads the model's PROSE is a coin flip across runs.** Three identical DVWA LOW engagements measured the same reflected XSS (`verified=True strength=verified context=html_body`, 25/25 characters surviving) and one of the three dropped it, because that run's model wrote "when … unescape" and a conditional-execution-claim guard matched the sentence. Prose varies run to run; a measurement does not. So scope a prose veto to the case it was written for — an effect nobody witnessed — by recording the deterministic witness (`literal_landing_witnessed`) at phase 5 and reading it in the gate AND in the FP cross-check's matching ground; keep the veto where no witness exists (the DOM path never sees a literal landing). Log and trace the veto you skip: the suppression that did not happen must be as auditable as one that did. → [narrative](../docs/lessons/README.md#lesson-43)
- **#44 — Three incidents in one methodology family is one defect, not three.** The upload class shipped a per-branch patch in three consecutive batches (`client_side_only`, `direct_execution`, `inclusion_chain`) before anyone asked what each branch actually CLAIMS. Give every branch a declared (effect, proving observation) pair, let only the branches whose observation the engine can make confirm, and emit leads for the rest — `inclusion_chain` asserted a consumer sink composes with the upload while verifying on a bare `status == 200` from a *direct* GET, and nothing in the engine reaches for a consumer. Then check the ORDERING: retrievability is trivially true whenever real execution would also have worked and the loop breaks on the first branch that verifies, so an LLM ranking alone decided whether a run reported CRITICAL execution or a HIGH "validation gap" on the same endpoint. Rank within each half; run the confirmable half first. → [narrative](../docs/lessons/README.md#lesson-44)
- **#45 — Fixing an origin-level finding's ADDRESS does not fix its VERDICT.** Making the security-header finding name the origin killed 12 of 16 flaky entries; the next ladder split the same header three ways anyway, because `(origin, header)` dedups on the first page to reach it and DVWA serves a CSP on exactly one path. Runs reaching `/` first reported the origin's CSP *missing* at medium; the run reaching `/vulnerabilities/csp/` first reported it *weak* at low. When a finding is scoped to a container (an origin, a host, a service), every field it carries — verdict and severity, not just the address — has to be a function of that container, or the race just moves. Settle it against a fixed member of the container (the origin ROOT), mirror any merge you already do in the other direction, and skip the rule when that member could not be observed. → [narrative](../docs/lessons/README.md#lesson-45)
- **#46 — A coverage assertion is only as sharp as the grade it reads.** The RANKING check ("a task dropped on a class's own primary target, for a class that emitted nothing") fired three times on a HIGH run against endpoints that were plainly other classes' pages — `_test_brute_force` on `/vulnerabilities/upload/#`, `_test_csrf` on `/vulnerabilities/exec/#`. Cause: `_endpoint_class_relevance` grades 0 on `param_match OR precondition_match`, and the form classes' precondition is the bare string `"form"`, so on an app where nearly every page posts something, grade 0 means "has a form" rather than "this class's surface". Before trusting an assertion built on a derived grade, check what that grade actually discriminates ON THIS TARGET — a signal that matches almost everything is not a signal. Narrow the assertion at the harness (require the class's own vocabulary when its precondition is generic), keep the excused entries visible, and record the engine-side imprecision as an open item with its blast radius rather than fixing it mid-ladder: a grader that decides which 150 of ~620 tasks survive invalidates every run already measured. → [narrative](../docs/lessons/README.md#lesson-46)
- **#47 — A docstring that states an invariant is not the invariant, and a safety rail is only as wide as its narrowest input filter.** Three of this branch's defects were invisible to a green 2136-test suite and only a real engagement found them. `secrets.py` claimed redaction was "applied at every writer that produces a durable artifact (trace, action log, report, state store)" — it was applied at ONE, so a login curl's own argv (`-d 'email=..&password=..'`) went verbatim into `trace.jsonl` and the tool-invocation records; the keyless test passed because it hand-wrote a body instead of going through a writer. Assert the PROPERTY at every writer, not the call site you remembered. Same shape for the classifier: `_PLAIN_VALUE` tested the WHOLE query value against `^[A-Za-z0-9_.\-]{1,24}$`, so `?action=delete` refused while `?action=Delete%20this%20record` sailed through and a crawler then re-sent it on every probe — when a filter exists to exclude OUR data, discriminate on the CHARACTER SET our data always carries, never on shape, and bound length per token rather than per value. And when the first fix broke DVWA's "Create / Reset Database" button, that named the missing distinction: the page's own words (path, keys, field names, labels) are read verbatim; only values we might have authored get filtered. Also: a kill switch armed at a mis-derived path (`clinkz abort ""` → `outputs/HALT`) is worse than none — the operator believes the engagement stopped while it keeps testing. → [narrative](../docs/lessons/README.md#lesson-47)
- **#48 — Redaction that knows what a secret IS cannot remove what a secret LOOKS LIKE, and a guarantee checked by the logic that produces it is not checked.** #47 moved redaction to every writer; a live authenticated run then wrote five session JWTs into `trace.jsonl` anyway — one decoding to a payload with the account's password hash and TOTP secret — because the registry only ever held values the OPERATOR supplied and the target ISSUED this one. Value-based redaction is structurally incapable of removing credential material the engagement captures; a secret needs a SHAPE vocabulary too, always on, registry or not. Worse, the check that reported "0 leaks" had searched for the configured values — it answered the wrong question truthfully, so re-read the ARTIFACT with an independent checker that shares the vocabulary but trusts nothing the write path claims (it found 826 shapes across 208 files where a human had spotted 5). Split the breadth: definite shapes fail the gate, the entropy heuristic is advisory and lives ONLY in the gate, because this engine's evidence is made of alarming-looking strings and a gate that cries wolf is a gate nobody reads. Same run, same shape, in the session counters: `session_losses_detected=15, reauthentications=0` where all fifteen were the engine's OWN anonymous controls — a 401 whose whole purpose is to prove the session works, counted as proof it broke. A watcher must be told by the request seam whether the request carried the session (it cannot infer it), must be disarmed until there IS a session, and must treat its own flag as a hypothesis the deterministic assertion adjudicates. → [narrative](../docs/lessons/README.md#lesson-48)
- **#49 — A phase timeout that discards the agent's return value converts an over-run into a total loss, and a budget checked only on the way in is not a budget.** The stated premise ("0 parameterised endpoints, so the engine only sees query strings") was wrong about its own evidence — the existing discovery produced 57/13 against the live target — and the real cause was in the planner's own prompt: `Endpoints (0 unique) []`, because the scan phase overran the generic 600 s timeout by nine seconds and that timeout force-kills the agent and throws its return value away. Verify a premise against the running target before building on it; express a cooperative budget as *is there enough left to FINISH the next unit of work* (it took THREE live runs: the first fix checked only "has it run out"; the second added the right check to ONE of four guards and a five-minute unlogged fuzz started with 104 seconds left, finishing 17s after the orchestrator gave up) — and check whether a retry loop can actually VARY its inputs, because expansion re-ran the identical scan three times for the same 112 routes; make the supervisor keep the partial; resolve a planned URL against a known origin and DROP it when there is none, because an unreachable probe is indistinguishable from a clean result; and run the container gate SERIALLY — sharing the single-tenant tools container with a live engagement produced three false failures that read exactly like a regression. → [narrative](../docs/lessons/README.md#lesson-49)
- **#50 — A total is not evidence about its parts, and a consumer that guesses a producer's field names fails silently forever.** Three defects shipped with one shape: an empty LLM planner absorbed by the class floor, a timeout absorbed by provider fallback, and 100% of ffuf's output discarded by a duck-typed seam absorbed by the crawler. Each time a component produced NOTHING, a fallback covered, findings still appeared, and no gate fired — because nothing measured a part. `_run_fuzz_tool` read `parsed.paths`/`parsed.directories` and `FfufOutput` has only `results`, so both `hasattr` were False and content discovery had never functioned; an empty list from a fuzzer is byte-identical to a target with nothing to find, and the green suite was part of the mechanism (`_MockFuzzOutput` declared `paths`/`directories` — names no real tool carries — so the test asserted a contract only the mock honoured). Declare the contract on the PRODUCER (`ToolOutput.discovered_urls` + `declares_discovery`) so a missing declaration is a loud DEAD SEAM rather than an empty list; never `getattr(parsed, "field", default)` over a model (sqlmap's `injectable` vs `vulnerable` returned False on every run for the same reason); make a mock mirror the real model, not the consumer's assumption; and ledger every component's ITEMS CONTRIBUTED, keeping "invoked and contributed zero", "cannot contribute", "never succeeded" and "declared but never invoked" apart, because they have different fixes. Same audit found the declared fallback chains were nominal (`try_until_sufficient` walks tool NAMES; every callback ignored its `tool_name` and re-resolved the capability, so `katana→gospider→hakrawler` ran katana three times) and four wrappers no agent resolves at all. And RUN the gate before claiming it: `corpus-replay` had no ffuf parser (304 records counted `no-parser`) — the parser gate did not cover the tool whose seam was dead. → [narrative](../docs/lessons/silent-degradation-and-the-dead-seam.md)
- **#51 — A measurement that reuses the object under test measures the test, not the deployment; and "correct" and "broken" both look like a zero.** Prompt caching shipped with a green suite and cost money for a week: the stability test handed the client the SAME `PromptSegments` object twice and asserted the two requests carried the same prefix, which is true of the mechanism and says nothing about the caller — production put the *engagement's growing endpoint inventory* in the cached span, presented on exactly ONE call per run, so across 154 traces there were 96,759 cache-WRITE tokens and **zero** reads, a flat 25% premium on that span. Read the recorded traces before believing any of the plausible causes (instability, provider failures, TTL were all falsifiable and all false); derive the break-even (`1.25 + 0.10(N-1) < N` ⟺ N > 1.28) and check the DEPLOYED N; split a prompt by *how often bytes repeat* and cache only the span a second call can re-present, so a miss costs noise; and make the cache a ledger component whose contributed item is `cache_read_tokens`, because "invoked, succeeded, contributed zero" is precisely what the ledger exists to catch and the cache was doing it while not being a component at all. Three siblings from the same batch: a parser must not assume it owns a foreign process's stdout (`whatweb --log-json=-` interleaves its brief log, so `json.loads` raised on every run and the CVE path ran starved — the fixture was a hand-authored clean array and the corpus baseline faithfully locked in `success: false` for 114 of 115 records); a permanently-silent-but-CORRECT component must be held apart from an alarming one, on a falsifiable discriminator (how far its own pipeline got — no input, or input containing nothing of its shape, is correct; candidates found and none emitted is the ffuf shape), never on self-assessment; and a class whose defining effect no existing oracle can observe emits nothing *correctly* — SQLi watched for DB errors, row-set deltas and UNION rows while an auth bypass returns 200 and a JWT, so the fix is a new indicator with its own shape-matched control, not a looser existing one. → [narrative](../docs/lessons/README.md#lesson-51)
- **#52 — A control that cannot reach the code path it targets reports a clean result.** The B-control for a relaxed suppression declared the login page as `JSON_BODY`, but the carrier dispatches on `ParamLocation` before consulting the form, so the "valid credential" arm actually submitted the engine's probe password and came back `confirmed=False` — the shape of a passing control, having tested nothing. Pin a control's *reason*, not its boolean (`no_auth_artifact_returned` is vacuous where `principal_is_an_identity_we_supplied` is the claim), print the wire bytes, give a suppression change its own control (a payload control refuses for unrelated reasons), and when the property is "this path is never taken" assert on the CALL (`await_count == 0`) — a behavioural test passes against a version that consults the model and discards its answer. Same rule for a control group: DVWA's zero auth-bypass findings mean something only because the trace shows the class ran and refused five times. → [narrative](../docs/lessons/README.md#lesson-52)
